What is real today

A prototype and a design

Two things exist. Atlas is a working React proof of concept with a synthetic estate, and the v3 canvas is a design of 28 screens. Neither one talks to a real enterprise system.

Atlas prototype · the code

22 views in one browser tab

Atlas is a React proof of concept. Its 22 workspace views are hash routes under one page, plus a separate /demo story. Workflow state lives in browser storage under the key atlas-demo-v3. No production backend API is implemented.

Atlas prototype · the estate

960 repositories, all synthetic

Six named records anchor the scenario, starting with commerce/order-service. A formula generates the other 954 across eight domains, which yields 245 applications and 2,875 service instances. Nothing in it was discovered by scanning an enterprise.

Atlas prototype · the connectors

66 connector cards, none connected

Integrations lists 66 descriptors in eight categories, and 39 start out marked configured. That flag is display state. Validation checks a prefix and a length, then waits. Nine model descriptors, four tools, six prompt templates and eight regression cases complete the kit.

v3 design

28 screens and one scenario

The v3 canvas draws 28 screens and two diagrams on one shell scoped to Dev. They follow one ticket, COM-2841, from Jira to a promotion request. Every integration in it is simulated, so the screens show what real data would look like.

The rule for both

Implemented, fixture or proposed

The handbook labels every claim. Implemented means present in the inspected code, fixture means prepared or deterministic sample data, and proposed means future design. Words on screen such as approved, connected or production describe fixture state or target intent.

what exists · October 2026
The honesty rule

Three labels on every claim

The handbook that documents Atlas states its numbers in one table and keeps the prototype's words apart from the platform's promises.

Atlas contains real local logic. It traverses a graph, ranks search results, runs eight evaluation cases, checks release-gate predicates and computes a configuration fingerprint, all inside the browser. What it does not contain is anything enterprise-facing.

Handbook 16.1 lists the gaps. There is no real enterprise login, identity federation, source-permission service, tenant isolation, model inference, repository connection, tool network call, durable agent runtime, backend audit ledger, deployment, rollback or Teams bot.

The v3 design follows the same rule on its own Architecture board. Phase 0 reads "28 screens, one complete scenario in Dev. Integrations simulated." The guide keeps a third layer for the production proposal and calls it proposed every time.

The ask

One slice, read-only, in Dev

Phase 1 connects four real systems for one domain and only reads from them. Four decisions start it, and five measures judge whether it has earned Phase 2.

Phase 1 · scope

Four real systems, one domain, Dev

Real Jira, Bitbucket, Jenkins and EKS, for one domain, in Dev only. Read-only first, so Vector reads tickets, pull requests, builds and pods and changes none of them. The Architecture board suggests Commerce as the domain.

Four decisions

What has to be settled first

The board lists four, all unchecked: the first domain, read access to sources in Dev, model hosting on Bedrock or Azure, and a pilot team for @B. Handbook 16.5 names the evidence each one needs and who is likely accountable for it.

Five measures

How Phase 1 is judged

Task success, lead time, escaped defects, evidence freshness and cost per task, each with a one-line definition on the board. None has a value yet, because nothing real has run.

Each phase earns the next

Evidence opens the gate

Phase 2 adds approved write actions, each with a person. Phase 3 adds domains and environments. For a functional slice the handbook asks for a reproducible authorized scenario, denied-access tests, failure recovery, and measured quality and cost. No dates are set.

What success means

Success changes with the stage

Handbook 1.9 sets a different bar for each stage. The five measures on the Architecture board are the bar for a working product, and the prototype is judged on something much smaller.

  1. Stage · the prototypeUnderstoodA reader completes the workflow, understands its evidence and recognises what is simulated.
  2. Stage · a functional productReal and reproducibleAuthorized real sources, reproducible artifact versions, genuine model and tool execution, meaningful quality measurements, recovery and observed deployment state.
  3. Stage · enterprise adoptionMeasured outcomesTask success, lead time, escaped defects, evidence freshness, cost per successful task and operational recovery. The number of logos in the connector catalog does not establish them.

Where they line up

Phases 0 and 1 describe the same steps. The board names the systems and the environment: Jira, Bitbucket, Jenkins and EKS, in Dev. The handbook names the ingredients of the same slice: one Git provider, an approved model behind a private endpoint, one language, retrieval, read-only tools, evaluation and trace.

After Phase 1 they cut the work differently. The board's Phase 2 adds write actions, with a person approving each one. The handbook's Phase 2 is a controlled pilot with IDE integration, durable runs, immutable bundles and a delivery adapter, and its proposed decision records favour durable execution before autonomous writes. The board's Phase 3 widens scope to more domains and environments; the handbook splits the later work into hardening and then federation.

This guide shows both as written and does not merge them. Neither is a schedule: the board says each phase earns the next with evidence, and the handbook calls its week and month ranges indicative planning estimates until identity, network, data permissions, enterprise standards, procurement and staffing are resolved.

Choices still open

Handbook 14.13 keeps the technology open. Relational databases, graph systems, search and vector options, event backbones, durable workflow engines, policy engines, editor strategies and serving options are alternatives to evaluate against enterprise standards. None is an installed dependency.

Ratifying one of the proposed decision records takes a decision owner, the alternatives considered, a date, the consequences and implementation evidence. The arithmetic is the proposal's own: calls ÷ 86,400 s gives the average, times the peak factor gives the peak, times the active duration gives open streams. At the example it gives 57.9, 579 and 2,315; the handbook rounds the average to 58 first and quotes about 580 and roughly 2,320. These are planning assumptions, not measurements. The day shape is illustrative; only its average and peak come from the sliders.

capacity envelope · handbook 14.11

Planning envelope

The proposal plans for 500 to 5,000 applications, 1,000 to 20,000 repositories, 10,000 to 100,000 components, millions of current relationships and potentially billions of historical observations. It also illustrates 48 million daily topology observations under one proposed workload, which is why it argues for aggregation and history tiering.

The prototype's 960 repository records demonstrate none of that. The handbook calls these planning assumptions, and the targets beside them are unratified: the local fixture timings do not measure any of them.

05 Know · Matrix, the enterprise graph

Every fact has a source

Matrix never stores a bare fact. Each relationship is an assertion with a source, evidence, a confidence and two clocks, and when sources disagree a person decides.

One identity

One service, five names

Git, the CMDB, Kubernetes, Optimus Logger and Jira each call order-service something different. Matrix ties the five names to one entity and leaves each system in charge of its own records.

Five systems

Five names for one service

Git knows commerce/order-service. The CMDB knows ORD-SVC-01, Kubernetes the label app=order-service, Optimus Logger svc:orders and Jira the component Orders. Each name is right inside its own tool, and no tool knows the other four.

Identity resolution

Resolved to one entity

Matrix records all five as aliases of one entity, so a question that starts from any of them lands on the same node. In the prototype that entity's ID reads service:8af2-orders. The production proposal asks for an immutable ID that the platform issues.

Authority per attribute

Each fact has one authority

The v3 board puts the rule in one line. The CMDB owns ownership, Kubernetes labels own runtime identity and Git owns the code. Optimus Logger and Jira contribute names only, and every system stays the source of truth for its own records.

Proposed · handbook 14.4

Names change, the ID stays

In the proposal each alias carries its source and the interval in which it was valid. A rename closes one alias and opens another on the same entity, so history from before and after the rename stays on one identity. A monorepo may hold many services, and one service may span several repositories.

Assertions

Every edge carries its evidence

"loyalty-consumer consumes order.confirmed.v2" is an assertion in Matrix. It arrives with the system that made it, the evidence behind it, a confidence and the times attached to it.

The record

What an assertion holds

In the prototype an edge records from, to, relationship, source, evidence file, confidence, observed time, valid-from date and status. The proposal adds the source revision, the collector and parser version, the environment, recorded time, a classification and an ACL fingerprint.

Three states

Verified, inferred, conflicting

Verified edges are drawn solid. The new call to fraud-risk-api is dashed because COM-2841 only proposes it. The loyalty edge is marked conflicting. The three states never merge, so a guess cannot quietly become a fact.

The conflict

Git says yes, Kafka says no

Git says yes with confidence 0.95, because the consumer is declared in loyalty/consumer.yaml on main. Kafka on msk-dev-use1 says no with confidence 0.90, because it has seen no consumer-group offsets for 48 hours. Matrix keeps both claims on the same edge.

Two clocks

When it was true, when Matrix learned it

Git's claim reads "true since Aug 2 · learned Aug 2". Kafka's reads "observed until Oct 11 10:40 · learned today 08:00". Keeping valid time apart from recorded time lets late evidence arrive without rewriting what Matrix knew before.

Reconciliation

A person decides

The board offers a likely reason. Dev runs loyalty-consumer 1.8.2, pinned in values-dev.yaml and still on the retired v1 topic, and R-2207 redeploys 1.9.0. A steward picks Keep and open COM-2856 or Mark retired, and the decision is recorded. No model settles the conflict by guessing.

How the prototype does it

Thirteen nodes, one loop

Atlas, the working prototype, holds the same neighbourhood as two local arrays. Its traversal and conflict handling are short and exactly documented, which makes their limits easy to state.

traverse() walks the static edge array breadth first from the selected entity. It skips inferred edges unless Proposed changes is ticked, and it never skips a conflict edge, so a disagreement is never silently cut out of a blast radius.

  • Results come back in entity-array order, with no paths, depths or edge evidence.
  • There is no depth limit, relation filter, time-interval evaluation or permission service.
  • Each visited node scans every edge, roughly O(V × E). That suits 13 nodes. The proposal plans for millions of current relationships (handbook 14.11).
  • For Order Service it returns 2 upstream and 8 downstream, or 10 downstream with the proposed call.
traverse() · paraphrased from handbook 5.4prototype
function traverse(start, direction, includeProposed = false)
  visited = { start }; queue = [ start ]
  while queue not empty
    id = queue.shift()
    for edge in edges              // all edges, every node
      if edge.status == "inferred" and not includeProposed
        continue                       // conflicts pass
      next = direction == "downstream"
        ? (edge.from == id ? edge.to : none)
        : (edge.to == id ? edge.from : none)
      if next and next not in visited
        visited.add(next); queue.push(next)
  visited.delete(start)
  return entities.filter(e => e.id in visited)
                                   // array order, no paths

Atlas prototype today

A 13-node Commerce fixture in local arrays, walked by breadth-first search over a static edge list. Confidences are fixed by status. The historical toggle only hides the inferred edge and evaluates no time, aliases are a prepared list, and the steward button writes a local flag and an audit string.

v3 design
  • order-service neighbourhood: 13 entities, 12 assertions, depth 2 hops
  • Now / Before COM-2841 / With COM-2841; verified, inferred and conflicting kept apart
  • Conflict inspector with per-source confidences and two clocks; a person decides
  • Five names, one identity, one authority per attribute
Production proposal

Immutable platform-issued IDs, with aliases that carry source and validity intervals. Observations stored apart from current relationships; each assertion with valid and recorded time; authority per attribute; a reconciliation owner for every contradiction. The graph is a rebuildable projection (handbook 14.4, 14.5).

Other ways to do it

Same question, other tools

Catalogs, CMDBs, trace maps, lineage standards and temporal databases each hold part of this picture. Vector's design keeps declared and observed claims side by side, with their sources and clocks, and hands disagreements to a person.

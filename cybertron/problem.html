The problem

Every change starts as an investigation

Before Venkatesh writes a line for COM-2841, he needs to know what the change will touch. Today that answer is spread across six tools, and each one has its own name for the same service.

COM-2841 · the question

Before any code, a question

Risk Engineering wants high-risk orders held for review before payment, "without changing the order event that 8 services consume." So the first job on the ticket is to find out what reads order.confirmed.v2 and what breaks if it changes.

The hops

Six tools, six sign-ins

The pieces sit in Jira, Confluence, Bitbucket, Jenkins, Amazon EKS and Teams. Each tool has its own login, its own vocabulary and its own name for order-service, and each holds one fragment. The person collecting them is the only thing that ties them together.

v3 Matrix · one service, five names

Same service, five spellings

Git calls it commerce/order-service, the CMDB ORD-SVC-01, Kubernetes app=order-service, Optimus Logger svc:orders and Jira "component Orders". Matrix, the enterprise graph, resolves them to one identity and gives each fact one authority.

Scale · synthetic estate

Then multiply by the estate

The prototype's synthetic estate has 245 applications, 960 repositories and 2,875 services in 8 domains, and the v3 Repositories screen shows the same totals. A change to any of them can start the same investigation.

The approach

Each system keeps its own records

Vector connects to the tools through Bridge and reads them where they are. Each connection says what Vector may do, each fact has one authority, and when two sources disagree, both stay on screen.

Bridge · v3

66 integrations, 39 connected

Bridge is where Vector meets the tools a team already runs: 66 integrations in 8 categories, 39 of them connected in the design. The Commerce team's own stack is 18 of them, from Jira and Bitbucket Data Center to Kafka and LaunchDarkly.

What Vector may do

Rights, per integration

Every connection lists what Vector may do. For Jenkins in Dev it may read jobs, builds and logs and receive build events. Re-running a stage needs an approval, and changing job configuration is not allowed. The binding names folder commerce/dev and agent pool k8s-build.

v3 Matrix · authority

Each fact has one owner

The CMDB owns who owns order-service, Kubernetes labels own its runtime identity and Git owns its code. Vector reads each attribute from the system that owns it and leaves the record there. Optimus Logger and Jira names stay as aliases.

When sources disagree

Both sides stay on screen

Git says loyalty-consumer reads order.confirmed.v2, at confidence 0.95. Kafka in msk-dev-use1 has seen no consumer-group offsets for 48 hours. Matrix keeps both, each with when it was true and when Matrix learned it, and a person decides. "No model settles a conflict."

How the prototype does it

A catalog of 66 cards

The Atlas prototype already has the catalog, in the same eight categories. Every card is a local descriptor, and no enterprise system is contacted.

Each descriptor has an ID, name, category, description, monogram, colour, a default configured flag, an auth description and a scope string. The auth and scope strings come from a rule per category, so they are display metadata, not provider permissions.

39 cards start configured. A saved override flips a card either way, and Reset returns to 39. Test connection checks the shape of the credential reference, waits 700 ms and marks the form tested. It never reaches the vendor, looks up the credential or checks a scope.

The rest of the estate is prepared too. Overview's 245 applications, 960 repositories and 2,875 services are fixed labels that match the generator at this snapshot, and its eight-node map is a drawing separate from the 13-node graph. Knowledge sources shows five aliases for Customer Profile as a prepared mapping, not a matching algorithm.

The two layers disagree on which 39. In the prototype, Jenkins, Bitbucket and Bitbucket Data Center start unconfigured and Delivery & discovery has none configured. In the v3 design, Jenkins and Bitbucket Data Center are connected. Only the totals match.

Production proposal

Federation over copying. Adapters read source APIs, snapshots, webhooks and telemetry; each entity gets an immutable platform-issued identity with external names as aliases; authority is set per attribute, and contradictions are kept with a reconciliation owner (handbook 14.4, 14.5). Phase 1 covers one domain with read-only tools (14.12).

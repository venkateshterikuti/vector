What reaches a model

Masked, and read as data

PII redaction masks names, emails and card data before any AI run reaches the model, 214 times this week. The prompt-injection shield makes agents and tools treat content as data, never as instructions. It has blocked 3, and at 09:47 it ignored an instruction found in a Confluence page.

Where data may go

EU data stays in the EU

The regional boundary keeps EU customer data in EU models and stores, with 0 violations. The Models board carries matching deployments, EU Reasoner on Bedrock and Embedder EU on Azure OpenAI, both marked Approved · EU.

Who must say yes

A person signs every change

Promotions out of Dev need the application owner and Application Security, bound to the exact bundle; order-service 2.14.0-rc2 is the one waiting. Write actions need a person, one action at a time. Two wait now: R-2207, @B's redeploy, for Sam Patel, and REQ-0042, a pull request from the Tools sandbox, for Maya Chen.

Spend and memory

Watch the budget, keep the record

Spend limits alert at 80% of the Dev budget and pause batch jobs at 100%. The budget is 72.3% used. This is the one policy marked Monitor, and the board does not spell out how Monitor differs from Enforce. Audit retention keeps runs, approvals and decisions for 400 days, tamper-evident, 1.2 M events so far.

Roles and checkpoints

Who can do what, and where it is checked

A role matrix decides who may run, edit, approve, deploy and configure. Source permissions apply on top, agents wait for a person on every deploy, and each decision lands in the audit.

Who can do what

Six roles, five actions

Developers, AI engineers, owners and Platform may run experiments. Only AI engineers edit prompts and agents. Only the owner and Security approve a promotion out of Dev. Developers and Platform deploy to Dev from a branch, and only Platform configures integrations.

Agents

One approval per action

The Agents column has a single mark, an approval on deploying to Dev. The footnote under the matrix reads “Agents (@B, Ratchet) deploy to Dev only after a person approves each action.” When Venkatesh asked @B to redeploy loyalty-consumer 1.9.0, the run became R-2207 and waits for Sam Patel.

Source permissions on top

A role opens no repository

The matrix says what a role may do, and the source system still decides what a person may see. On Oct 12 Sentinel let @B read the payments-gateway repository with Tomás's permissions. In Teams, a question about a restricted page gets a private message with only what the asker may see.

Proposed · four checkpoints

Checked before each step that matters

The production proposal checks access before retrieval, before content reaches a model, before cached or derived results are served and just before any side effect. Cache keys carry identity and source revisions, revocation reaches retained access, and repository text, documents and tool responses stay data that cannot override policy.

How the prototype does it

Six switches and a list of strings

Atlas, the working prototype, has a Governance view with six policy switches, a drawn role matrix and an audit tab. The handbook is exact about what each one touches, and none of them enforces anything outside the browser.

Each policy is a Boolean in shared state, and all six start on. The whole policies object is part of the configuration fingerprint, so flipping any switch while a release is staged or awaiting approval returns it to Draft and clears its approvals (7.5). Five switches also sit in the fourth release gate. The budget switch is left out of it on purpose (7.4).

The eight evaluation cases never read those switches. A separate guard switch, labelled Safety policies in the Playground, decides the timeout, injection and PII cases. Turning off pii alone leaves the evaluation at 8 of 8 while the gate blocks the release; turning off guard fails three cases at once (7.8). The v3 preview puts both effects under one policy.

The Access & roles tab draws a four-role matrix that does not disable any control, and no authentication backend exists (7.9). Audit is a newest-first array of strings shared by Releases and Governance. The browser user can alter or clear it, and strings keep arriving when the audit switch is off (7.10, 16.2).

Atlas prototype today

Six Boolean policy switches, all on by default. They change the fingerprint, and five of them feed the fourth release gate; a separate guard switch drives the three safety eval cases. The role matrix is drawn and disables nothing. Audit is a list of strings in browser storage.

v3 design
  • Seven policies with scope, counter and Enforce or Monitor
  • A preview of eval and release effects before a change
  • Six roles × five actions, source permissions on top
  • A person for every agent deploy and write; recent decisions and audit export
Production proposal

Enterprise SSO and workload identity, with roles combined with tenant, project, application, environment, classification and region. Checks before retrieval, before a model, before cached results and before side effects, and approvals bound to the exact proposal, environment, policy version and expiry (handbook 14.7, 14.9).

Other ways to do it

Same job, other tools

Policy tools fall into two families: engines that answer allow or deny for a request, and model guardrails that mask or block content. Sentinel's design puts both kinds of rule on one screen.

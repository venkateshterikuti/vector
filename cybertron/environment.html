04 Foundations · the v3 rule

One environment per window

You pick Dev once, in the title bar. From then on every screen, terminal, agent and @B run in that window is about Dev, and nothing on screen offers a second environment.

one picker · 28 screens follow it
Why the rule exists

Every screen had its own answer

The first screen set let each screen choose its own environment. Version three removed every one of those controls and kept a single picker.

Before v3 · the 28-screen set

Four screens, four answers

Clusters opened on "All" and showed five clusters side by side behind Dev, QA, Stage and Prod tabs. Pipelines ran one track from Dev through Stage to Prod. Optimus Logger opened on Prod while Traces showed Dev, and CodeX had a terminal for each environment. Nothing told you which environment a fact came from.

Rule 1 · one picker

Chosen once, in the title bar

The environment lives only in the title bar, beside the application picker. No screen has its own tab, slider, list or badge for it. Each window tells you its environment in one place, and every screen reads it from there.

Rule 2 · it lives in the URL

Links and refreshes stay put

The address carries /env/dev/…, so reloading a page or opening a link a colleague pasted lands in the same environment it was copied from.

Rule 5 · switching resets

Change it, and everything reloads

Picking QA clears every screen's state and caches, then reloads them in QA. Nothing from Dev survives the switch, so no screen can keep showing stale Dev data under a QA label.

The flow

How a request stays in Dev

The picker is only the visible end. Underneath, the environment travels with every call, the API checks it, and one registry turns the word "Dev" into real accounts, clusters and topics.

1 · Vector app

EnvContext holds one value

The picker writes env = "dev" into EnvContext. The 27 screens and @B all read it. None of them has an environment control of its own.

2 · Rule 3 · every call carries it

X-Vector-Env: dev

Every request the app makes sends the header X-Vector-Env: dev. A request without it, or with a different value from the window it came from, is a bug the gateway can catch.

3 · Control plane

The gateway and Sentinel check it

The API gateway asks Sentinel whether your role allows this action in Dev, and rejects any resource ID that belongs to another environment. A Prod pod name pasted into a Dev window is refused there.

4 · Rule 4 · one registry defines it

"Dev" becomes real targets

The env registry is the one place Dev is defined: AWS account northstar-dev, cluster nsx-dev-use1/commerce, Jenkins folder commerce/dev, Kafka msk-dev-use1, flags, secrets and the model region. Screens never hard-code any of them.

5 · Plane services

Every record comes back tagged

Each plane resolves its systems through the registry and answers as Dev: Jenkins and EKS for execution, Kafka and Git edges observed on msk-dev-use1 for knowledge, and logs, traces and the AWS bill tagged env=dev for telemetry.

Rule 7 · shared tools still show

Scoped screens and shared screens

Jira, Bitbucket, Confluence and Teams are not per environment, so their screens appear in every window. Any runtime fact on them, such as the running version, its pods or its last deploy, is Dev's.

Rule 6 · promotion is an action, not a view

The only way out of Dev

Because a window shows one environment, moving a release forward cannot be a matter of looking at two environments side by side. GroundBridge files a request instead, and the run shows up when you switch to the next environment.

In the design

Where you see it on screen

Three boards from the v3 canvas carry the rule: the title bar on every screen, the open picker, and the flow diagram. Select a plate to open the full screen.

Plate 04.1 · every screen's title bar

The picker and the strip

  1. The picker. "Dev us-east-1", tinted blue, sits beside the application picker. It is the only environment control in the app.
  2. The environment strip. A thin bar under the title bar spells out what Dev resolves to: AWS account, EKS namespace, Jenkins folder, Kafka cluster, flags, secrets and model region.
  3. What you may do. "Read & write · promotions go to QA" states your rights in this environment and where releases go next.
  4. Application, separately. Commerce Orders scopes by team. Application and environment are the two pickers, and both are global.
Plate 04.2 · the picker, open

The only list of environments

  1. Scope of the choice. "Applies to every screen, terminal, agent and @B run."
  2. Rights per environment. Dev is read and write, QA is read and exec. Each row names its AWS account and cluster.
  3. Prod spans two regions (nsx-prod-use1, euw1) and is read only.
  4. The promise. "No screen ever shows two environments at once. This menu is the only place they're listed."
  5. Strip previews. The strip under the title bar follows the selection, including where promotions go next.

Production proposal

Attribute-based access that includes environment, checked before retrieval, before content reaches a model, before cached results are served and just before any side effect, with cache keys scoped to identity and permissions (handbook 14.9).

Other ways to do it

Same question, other tools

Most tools that span environments pick one of two habits: scope the whole view to one, or show several side by side. Vector chose the first, for every screen.

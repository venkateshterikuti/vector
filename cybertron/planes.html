One ticket, five planes

Each plane does one kind of work

The Architecture board tells the story of COM-2841 in five numbered steps, one per plane. Follow the question about build #418 from the person who asks it down to the record of what it cost.

1 · Experience · where people work

A question in Teams

Venkatesh asks @B why build #418 failed on COM-2841. Experience covers every place people work: Home, CodeX (the IDE), Threads, Reviews, and @B, the Teams bot, pronounced "bee". The question leaves this plane carrying who asked and which environment the window is in.

2 · Control · decides what may happen

Sentinel decides first

Sentinel, the governance service, checks the request before anything runs. Reading the build is a read, so it runs with Venkatesh's own permissions. Promoting order-service 2.14.0-rc2 to QA is a different kind of action: it waits for Maya Chen, the Commerce application owner, and Lena Fischer from Application Security.

3 · Execution · runs the work

Ratchet re-runs the tests

Ratchet, the pipeline agent, traces the failure to commit a41c9e2, which adds riskDecision to an order event whose v2 schema rejects unknown fields. After fix 5c0d7e1, build #419 re-runs from contract tests, passes all nine stages at 11:04 and deploys to nsx-dev-use1 at 11:09.

4 · Knowledge · what is true, with sources

Matrix supplies the reason

Matrix, the enterprise graph, links order-service to order.confirmed.v2, the topic eight services consume, and to ADR-031, which puts new fields on a v3 topic. The fix therefore keeps riskDecision internal, and the v3 topic is tracked in COM-2867.

5 · Telemetry and cost · what happened, what it cost

Every step leaves a record

Each step is traced, evaluated and charged to Commerce in Dev. Optimus Logger, the team's existing observability tool, holds logs and metrics; Traces shows the spans of each run; Evals scores eight cases on configuration cfg-7f3a9c; Cost attributes spend to a team and an application.

Cross-cutting

Six concerns run through every plane

The Architecture board draws them as a column beside the five planes. Each one applies at every plane, on every screen, whichever plane happens to be doing the work.

  1. New in v3EnvironmentOne per window, chosen in the title bar. Every call carries X-Vector-Env and one registry resolves the targets. Chapter 04 follows it end to end.
  2. Prototype · identity and authorizationIdentity@B and the tools act with each person's own permissions, and source permissions still apply on top. The new call to fraud-risk-api uses workload identity, with no static secret.
  3. Prototype · data classification and encryptionClassificationNames, emails and card data are masked before the model (214 this week). EU customer data stays in EU models and stores. A restricted page goes to a private message.
  4. Prototype · audit and OpenTelemetryAuditRuns, approvals and decisions are kept 400 days, tamper-evident, and the Sentinel board counts 1.2 M events. A note sent to approvers is stored in the audit log too.
  5. Prototype · budgets and rate limitsBudgetsThe Dev budget alerts at 80% and pauses batch jobs at 100%; it stands at 72.3% of $6,000 (illustrative). Agents carry their own caps, such as $0.01 per run.
  6. Prototype · version lineage and provenanceLineageResults are bound to a configuration fingerprint, cfg-7f3a9c, and releases to a bundle digest. In Vault, "a new input — even one parameter — produces a new fingerprint and a new version."

The prototype's Architecture inspector lists the same cross-cutting items for every layer, five of them, named in the small labels above (handbook 14.14). The v3 design adds environment as the sixth.

Around the edge

Bridge links the tools teams already use

Tickets stay in Jira, code in Bitbucket, builds in Jenkins and pods in Amazon EKS. Bridge connects 66 such systems in eight categories, 39 of them connected in the design, and the Architecture board says it in one line: "Vector links these systems; it does not replace them."

Production proposal · handbook 14.2

What each plane must be good at

The handbook's proposal gives four of the planes a property they must hold. These are proposed, and nothing in the prototype implements them yet.

Control · proposed · 14.2, 14.3

Validated, transactional changes

Policy, approvals, artifact versions and the release ledger change through checked transactions. Each change names its tenant and project, the authenticated subject, a schema version, an idempotency key and the resource version it expects, so a write based on a stale version can be refused with a structured error.

Execution · proposed · 14.2, 14.8

Regional and bounded

Workers run in region-pinned, isolated pools and hold short-lived, narrow grants. Every run has limits on wall time, steps, tools, tokens, cost, parallelism and output. The v3 fraud-review agent shows the idea: at most 8 steps, a 10 s timeout and $0.01 per run, on nsx-dev-use1.

Knowledge · proposed · 14.2, 14.5

Ingestion on its own clock

Sources feed replayable observations into an event log, and the graph, search and vector projections update from it. Because ingestion is asynchronous, a stale source does not automatically stop work that is already approved. Its watermark falls behind, and answers can show the age of the evidence behind them.

Telemetry and cost · proposed · 14.2

Two separate questions

Telemetry must keep operational success apart from answer quality. The v3 Traces board puts it plainly: "A run can finish in 1.8 s and still make the wrong call." Evals answers the second question. With safety off, T03, T04 and T08 fail; with the threshold at 0.95, T02 and T06 fail.

How the prototype does it

A map of proposed boundaries

Atlas, the working prototype, has an Architecture view too. It explains the proposed layers and links into other views; none of its layers is a running service.

The view draws five layer cards from a catalog called architectureLayers. Execution is selected when the view opens. Clicking a layer's title updates the inspector with that layer's description, deployment boundary and core contract; clicking a service tile opens a workspace instead, which is why several services open the same view (Tool / MCP gateway opens the Tool registry, Sandbox workers open Environments).

The inspector's cross-cutting list is the same for every layer, and a six-step strip, Authorize, Assemble, Execute, Validate, Observe and Promote, explains a request. The handbook calls the strip "static explanatory content, not a live execution monitor".

The cut differs from v3 in one place. The prototype's fifth layer is an integration fabric, and telemetry appears only as a cross-cutting item. Handbook 14.2 and the v3 board make telemetry and cost a plane of its own and move the integrations around the edge as Bridge.

Five planes, one browser tab

Underneath the prototype's layer cards there is a single React app. Business actions run in the client, state lives in one provider and is saved to local storage, and every record comes from local fixture arrays. The handbook is explicit that screen names are not evidence that similarly named backend services exist.

The proposal keeps the same caution in the other direction: the themed names "do not prescribe one microservice, database, or team per name". It suggests starting with a small deployable set and splitting only when operational evidence warrants it (14.1).

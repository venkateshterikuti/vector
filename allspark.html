Prompts · fraud-review v7

A prompt with typed variables

Risk Engineering owns fraud-review v7; Priya Raman last edited it on Oct 11. The system message says to use {{context}}, call fraud-risk-api exactly once, return a FraudDecision and decide manual_review when the score is at least {{threshold}}. Each variable has a type: a retrieval recipe, a number that defaults to 0.80, and order JSON validated against OrderInput.

Output schema and versions

Held to FraudDecision

The schema allows two decisions, a score from 0 to 1 and at most three reasons. Every version records what changed and how it scored: v5 added the PII rule (6/8), v6 capped reasons at three (7/8), v7 fails closed on a tool timeout (8/8). Saving creates v8, and fraud-review-agent stays on v7 until someone switches it.

Settings and guardrails

Every setting is part of the configuration

Temperature 0.2, review threshold 0.80, 1,024 output tokens, PII redaction, the injection shield, the FraudDecision schema check, two tools and four context items from Commerce + Risk. Together they are configuration cfg-7f3a9c. The screen states the rule under the settings: "Any change here creates a new configuration. Evidence from older runs no longer counts toward a release."

Compare · ORD-10482

Three answers to one order

Risk Reasoner 3 on Bedrock returns manual_review at 0.91 with three reasons. General Reasoner on Azure OpenAI also holds the order, at 0.87, with two. Local Llama, self-hosted on vLLM, approves at 0.64 after skipping the fraud-risk-api call the prompt requires.

What the comparison shows

Speed and price don't decide

Local Llama is the fastest (0.92 s) and the cheapest ($0.0009 a run, an illustrative figure), and it approves a risky order. General Reasoner is quicker than Risk Reasoner 3 and misses T07, the event contract case. Only Risk Reasoner 3 passes all 8 cases.

Agents and tools

Agents wait, tools ask

An agent in Agent studio is a flow of typed steps you can read top to bottom. Tools come from a registry that marks each one read or write, and a write always waits for a person.

Agent studio · fraud-review-agent v3

Seven steps, one waits

When order-service asks for a decision, the agent retrieves 8 results from Commerce + Risk, calls fraud-risk-api, reasons with Risk Reasoner 3 using fraud-review v7, checks the output against FraudDecision and for PII, branches at 0.80, and asks a person before create-jira-ticket. It runs on a LangGraph runtime on nsx-dev-use1 with at most 8 steps, a 10 s timeout and $0.01 per run.

Step 3 · Call tool

Fail closed after 800 ms

The tool step pins fraud-risk-api 2.4.0 (OpenAPI, Risk Engineering, scope risk:score) and passes order_id and amount. It has an 800 ms timeout and one retry. If the API still does not answer, the step fails closed and the prompt's rule turns that into manual_review. The call runs with the caller's permissions.

Test run · ORD-10482

Nothing was written

Context took 140 ms, the tool returned 0.91 in 220 ms, reasoning took 1,280 ms and the checks passed in 90 ms. The run ends at manual_review with the ticket step waiting for approval. In the design's words: "Nothing was written; the ticket step waits for a person."

Tools · registry

Read sees what you see

Commerce Orders has four registered tools. fraud-risk-api (OpenAPI) and enterprise-search (MCP) only read, and only what the caller could read anyway. create-pull-request (Git adapter) and deployment-request (event) write, and "Write tools always need a person to approve the exact action."

Sandbox · create-pull-request 1.3.0

A write becomes a request

The sandbox runs in Dev with your own permissions. Running the write tool opens nothing on Bitbucket. It returns approval_requested as REQ-0042, bound to the input digest sha256:41be…09d and to the caller, with external_action: false. A different input has a different digest, so this approval cannot cover it. Maya Chen decides in Approvals.

How the prototype does it

A fixture with a real fingerprint

Atlas calls no model. The run is a timed fixture, but the configuration fingerprint is real string comparison, which is enough to show the release rule working.

In the Atlas prototype, AllSpark is a proposed name over the Playground, Prompt library, Agent studio, Model gateway and Tool registry views (handbook 6). Run checks that the input parses as JSON, waits 900 ms and returns the same answer every time: order ORD-10482 at risk 0.91, manual_review when 0.91 is at least the threshold, otherwise approve. The amount you type does not change it. Latency and cost are copied from the model descriptor, and tokens are estimated from the prompt's string length.

Most settings only change the fingerprint. That still proves the point: move the temperature and the 8/8 evaluation goes stale, though the fixture answer is identical. Compare models lists the first three built-in descriptors with their fixed latency; it does not run them. Agent studio holds an ordered list of step names, and Test workflow calls the same fixture without waiting at a human step.

The model gateway starts with nine aliases, all Approved. Capability admission is not implemented: Open Reasoner 70B lacks tools and still runs the preset (6.7).

The routing order is the production proposal (handbook 14.7: authorization and data policy first, capabilities second, capacity third, preferences such as cost or latency afterward). The catalog is the v3 Models board: provider, residency, capabilities, price per 1M tokens, p50 and status for all ten aliases. In the design a team names an alias and the gateway routes that alias to a deployment; running the order across the whole catalog is this lab's illustration.

Residency must match exactly, because the design does not say which region the Private VPC is in. Capacity uses the only quota the design shows (Risk Reasoner 3, 600 req/min for Commerce in Dev); for the other aliases capacity is not shown in the design, so they pass unchecked. Prices are illustrative, and aliases billed as compute have no per-token price, so p50 breaks that tie.

Atlas prototype today

No model is invoked. A run is a 900 ms fixture that always returns ORD-10482 at 0.91, and most settings only change the fingerprint. Agent studio is a list of step names; nine model aliases all start Approved; a custom endpoint passes five string checks and becomes "Registered · untested". Write tools in the sandbox return demo-request-0042, with no approval bound to the input.

v3 design
  • Compare three models on one order, with steps, evals, latency, tokens and cost
  • Versioned prompts with typed variables and the FraudDecision schema
  • Ten-alias catalog with residency, quota, fallback and approval
  • Agents as explicit flows; a write tool becomes REQ-0042, bound to its input digest
Production proposal

Model descriptors that name a tested deployment, data-classification ceiling and quotas; routing by policy, then capabilities, capacity and preference; tool contracts with risk class, scopes, idempotency keys and a side-effect ledger; approvals bound to the exact proposal, environment, policy version and expiry; durable sequential agents first (handbook 14.7, 14.8).

Other ways to do it
